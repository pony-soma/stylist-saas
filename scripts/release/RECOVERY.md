# 初回本番切替のバックアップ・復旧手順案

状態: **手順の準備のみ。バックアップ取得・復元・本番停止は未実施。**
本書は本番作業の承認ではない。承認対象に停止時間、対象コミット、移行SQL、
バックアップ、復旧方針を含め、各ゲートの証跡を揃えてから実行する。

## 今回の復旧方針

- 移行前の旧アプリには広いアクセスを許すRLSとの組合せがある。旧デプロイへの
  単純な戻しを「安全な復旧」と扱わない。旧RLSを公開状態で復元しない。
- 新アプリは新しい課金・所有者テーブルを必要とする。DBを旧版へ戻して新アプリ
  を開放する組合せも不可。障害時は停止を維持し、原則として修正して前進する。
- 過去の所有者不明カルテ・写真・旧契約は保持する。見えないことと消えたことを
  区別し、勝手な所有者補完や削除をしない。
- アプリのHTTP停止だけでは、既存ブラウザからのSupabase直接通信、Storage、
  旧デプロイURL、DB接続、Cron、Edge Functions、外部のStripe操作は止まらない。

## バックアップ範囲と証跡

| 対象 | 確保するもの | 確認方法 |
| --- | --- | --- |
| PostgreSQL | データ、スキーマ、制約、索引、RLS、関数、権限、必要なAuthデータ | バックアップ方式ごとの対象一覧と隔離先での復元結果 |
| Authの設定 | OAuth設定、許可URL、必要な秘密情報の安全な参照先 | DB復元だけで設定・認証が戻ると仮定せず、試験用ログインで確認 |
| Storage | 実ファイル、対応するメタデータ、バケット設定・ポリシー | 件数、サイズ、内容ハッシュ、試験用画像の読出し照合 |
| アプリ | コミットSHA、デプロイID、ビルド条件、ドメイン設定 | 本番対象と復旧候補の接続先・互換性を照合 |
| 環境変数 | 名前・適用環境・安全な秘密情報保管先 | 公開キーも含めて本番/検証の混在がないことを確認 |
| Stripe | 本番アカウント、商品/価格/Portal/Webhook設定、照合開始時刻 | Stripeの状態とDBの課金状態・処理済イベントを突合 |

SupabaseのDBバックアップはStorage実ファイルを含まない。DB内のメタデータを
戻しても、削除済みのファイルは復元されない。利用可能なバックアップ方式・保持
範囲・復元権限を対象プロジェクトで確認する。復元には停止時間が生じる。
[Supabase: Database Backups](https://supabase.com/docs/guides/platform/backups)

バックアップの実体は公開Git、CI成果物、この会話、一般の検証環境に置かない。
暗号化・アクセス制限・保存期限・削除責任者を定めた専用保管先を使う。
本番顧客データやAuthの検証環境への複製は行わない。リハーサルはダミーデータで
行う。本番バックアップの実復元検査が必要なら、別途承認した閉鎖された復旧先を
使い、送信・課金・外部ジョブを遮断する。認証情報をログに出さない。

CLIによる論理バックアップを選ぶ場合は公式手順と実際のCLIバージョン・helpを
確認し、スキーマだけのdumpを完全バックアップと扱わない。Auth、Storageの
メタデータ、必要なロール等の範囲を確認し、復元可能性を試験する。
[Supabase: Backup and Restore using the CLI](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)

## 承認後の取得・切替順序

1. 対象コミット、DB、Vercel、Stripeの本番アカウントを再確認する。
   現在のデプロイIDと構成、実行開始時刻を秘密情報なしで記録する。
2. 検証済みの停止デプロイを有効化する。一般画面、ログイン、API、Webhookを
   HTTP 503にし、新しいCheckout作成を止める。停止画面に戻ったことだけで
   成功とせず、代表パスと直接デプロイURLを確認する。
3. 開いているCheckout/Portalの操作は停止画面で止まらないため、対象と時刻を
   記録する。Webhookへの503は成功処理ではない。未配信イベントを記録し、
   復旧後に再送・照合する。受信前に200を返して破棄する運用はしない。
4. 検証した別手順でSupabase直接アクセス・バックグラウンド処理を制御する。
   実行中リクエスト/トランザクションを排出し、書込みが止まったことを確認する。
   未検証の接続強制切断、APIキー変更、権限一括変更はその場で行わない。
5. 同じ停止期間内でDB/AuthとStorageの整合したバックアップを確保する。
   前後の件数、ファイル一覧/ハッシュ、開始終了時刻、バックアップ識別子を
   非公開の作業記録へ残す。取得途中の失敗は切替中止条件。
6. `preflight.sql` を再実行し、想定外の差分がなければ承認された順序でStorage
   非公開化、DB移行、本番用環境変数によるアプリ配置を行う。停止は維持する。
7. 所有者分離、唯一のマスター、旧データ保持、写真の直接取得拒否、課金状態を
   確認する。Webhook再開前に本番署名検証と冪等処理を確認する。
8. 停止解除用デプロイの接続先・設定を再確認する。アクセスを再開した後は
   Stripe未配信イベントを再処理・照合し、重複課金/二重更新がないことを確認する。
   解除後にしか確認できない項目が失敗したら、直ちに停止状態へ戻す。

## 障害時の判断

| 発生時点 | 初動 | 禁止する短絡的な対応 |
| --- | --- | --- |
| バックアップ前/移行前 | 停止維持、原因調査。再開するなら元構成と安全性を再確認 | 未確認バックアップで続行 |
| SQLトランザクション失敗 | ロールバック結果を照合。別操作で変えたStorage等も確認 | SQL失敗を理由に全外部設定も元通りと判断 |
| DB移行済・利用再開前 | 停止維持、新DB互換の修正版を準備。復元は承認された計画で実行 | 旧アプリへ単純ロールバック、公開バケットへ戻す |
| 利用再開後 | 再停止し、バックアップ以降の更新とStripe状態を保全・突合 | 新しい予約/契約を捨てる盲目的な全DB復元 |

DBを復元する場合は、対象時点以降に失われる更新を先に特定する。必要な差分を
安全に保持してから、承認された復旧先・時点へ復元する。復元直後は旧い広範なRLSや
公開バケット設定が戻る可能性を確認し、アクセスを閉じたまま必要な安全化を行う。
Storage実体とメタデータの対応、Auth参照、課金状態、デプロイとの互換性を照合する。
Stripeの決済・解約はDB復元では巻き戻らない。現在のStripe状態を再取得して整合し、
返金や契約取消を復旧のついでに実行しない。必要な場合は別途承認を得る。

## Vercelの戻しに関する注意

Instant Rollbackは以前のビルドへドメインを戻す操作で、外部DB/Storage/Stripeを
戻さない。古いデプロイには古い設定が残る。ロールバック候補の利用可否はプラン等で
異なるため実際に確認する。また、ロールバック後は本番ドメインの自動割当が停止する
ため、復旧完了時に意図したCI/CD状態へ戻っていることも確認する。
[Vercel: Instant Rollback](https://vercel.com/docs/instant-rollback)

環境変数変更は既存デプロイへ反映されず、新しいデプロイが必要となる。
停止フラグを保存しただけで停止完了と扱わない。本番設定で作った停止候補を検証する。
検証用Supabase公開キー等を埋め込んだ成果物をそのまま本番へ昇格しない。
[Vercel: Environment variables](https://vercel.com/docs/environment-variables)

公式資料確認日: 2026-09-16。操作当日は対象アカウントの権限・設定・復元範囲を再確認。

## 自動リハーサルの範囲

CIの `tests/e2e/recovery-rehearsal.mjs` は固定のローカルSupabaseのみで動く。
合成データの専用DBをpg_dumpし別DBへpg_restoreした後、行内容・SELECT権限・
所有者RLSを検証する。専用の非公開StorageバケットでダミーPNGの取得・削除・
再アップロード・SHA256一致と公開URLからの取得拒否も確認し、専用資源を削除する。

これはバックアップ・復元手段の基本確認であり、LiNo全スキーマ、Authログイン、
本番Storageメタデータとの整合性、暗号化保管、別プロジェクトへの復旧を証明しない。
本番バックアップ権限と復元リハーサルの未完了ゲートは引き続き残す。
